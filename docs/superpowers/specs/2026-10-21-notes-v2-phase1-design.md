# 筆記 App v2 — 整體決策與第 1 階段「本機核心」設計規格

- 日期：2026-10-21
- 狀態：待審閱
- 範圍：本文件記錄 v2 全部已定案的產品決策（供後續階段參考），並詳細規範**第 1 階段：本機核心**的設計。第 2～5 階段各自另寫規格。

---

## 1. 目標

把現有的個人 Markdown 筆記程式（v1，Next.js，`v1-archive` 分支）重寫成一個**可以給大眾使用的筆記產品**：

- 本機優先（local-first），不登入即可完整使用；日後可選擇註冊並在多台裝置間同步
- 使用者可能存放隱私資料，雲端資料採端對端加密
- Notion 式區塊編輯、Obsidian 式介面結構、Apple 式的質感與細節
- 現階段專注電腦（Windows / macOS + Chrome），架構預留桌面 App 與手機平板

成功標準（第 1 階段）：不登入、純本機，就能完整取代 v1 的日常使用，並達到第 13 節的品質門檻。

## 2. 已定案的產品決策（全階段）

### 2.1 資料
- 正本是**區塊資料（Yjs CRDT）**；Markdown 只用於匯入、匯出與鏡像
- 自動鏡像 `.md` 到使用者指定資料夾：必要功能、**單向**（App → 資料夾）、維持資料夾結構、支援 Chrome / Edge 桌面版；其他瀏覽器用手動匯出
- 外部修改 `.md` 自動回寫：不做（第一版）
- 匯入、匯出全面採用新格式；ZIP 匯出的路徑為 `資料夾/標題.md`
- 不支援 Markdown 內嵌 HTML；匯入時轉為純文字保留

### 2.2 運行形式
- 網頁版（PWA）優先，架構預留桌面版轉接層（Tauri）
- 現階段專注電腦；手機平板之後處理，目標是做成 App

### 2.3 帳號（第 3 階段）
- 不登入可使用（純本機模式），想同步再註冊
- 只支援 Email + 密碼；註冊時提供復原碼；忘記密碼只能找回帳號，無法解開雲端舊資料
- 資料模型：使用者 → 裝置 → 知識庫 → 筆記／附件 → 分享連結
- 多人協作暫不做，結構預留

### 2.4 同步與隱私（第 3 階段）
- 範圍：同一使用者的多台裝置
- 伺服器：Supabase 免費方案，同步層為可替換的轉接層；不自架、早期不付費；現階段不限制附件容量
- **端對端加密**：筆記在裝置上加密後才上傳，雲端只存密文

### 2.5 分享（第 4 階段）
- 拿到連結即可開啟，收件者不需輸入任何東西；金鑰放在連結 `#` 之後，伺服器看不到內容
- 分享前設定：預覽或可存取、快照或即時同步、是否包含附件、有效期限、密碼保護（選擇性）、隨時撤銷
- 「可存取」= 收件者可下載（.md / PDF），也可存副本到自己的知識庫（不需註冊，存入本機知識庫）
- 不提供「禁止複製」

### 2.6 編輯器
- 單一所見即所得，沒有預覽模式，不提供原文檢視
- 編輯器框架：**Tiptap**（ProseMirror）
- 筆記標題：Notion 式標題區塊，整個知識庫內不重名
- 清單編號：Notion 式（依層級 `1.` → `a.` → `i.`，可手動改為數字、字母、羅馬數字）；中文數字與天干地支不做
- 註腳：先不做
- Slash 選單、清單操作、自動編號、程式碼高亮（含 ABAP）、KaTeX、Callout 全部重寫，v1 程式僅作參考

### 2.7 介面
- 主畫面採 **D 方案**：B「紙本」為主 + A 的資料夾收納方式 + C 的隱藏式圖示工具列（設計稿：「筆記主畫面設計方向」畫布第二列）
- 經典 Apple 風為底，液態玻璃只用於短暫浮出的元件
- 預設淺色、一套預設樣式可微調；移除自訂游標、深色主題切換、水墨背景；保留使用者自訂背景
- 外觀設定隨帳號同步

## 4. 第 1 階段範圍

### 4.1 包含

**區塊**：段落、標題（H1～H3）、引用、分隔線、項目清單、編號清單、待辦清單、提示框（Callout）、程式碼區塊（語法高亮含 ABAP）、表格（增刪列與欄、調整欄寬）、圖片、影片。

**文字格式**：粗體、斜體、底線、刪除線、行內程式碼、網址連結、文字顏色、螢光標記。

**編輯操作**：Slash 選單、選取文字時的浮動格式列、區塊拖曳排序、清單縮排與子樹上下移動、復原／重做、貼上（純文字與 Markdown 文字轉成區塊）。

**連結與組織**：
- 筆記連結 `[[筆記]]`
- 區塊連結：連結到另一篇筆記中的任何區塊（標題、段落、清單項目、程式碼、表格等）
- `#標籤`
- 反向連結（已連結、提到但未連結）、大綱
- 資料夾樹（巢狀、拖放、排序）、垃圾桶（保留 30 天）
- 全文搜尋、快速切換面板

**介面**：D 方案完整版面、自動調整版面、側欄與右側卡片寬度拖曳、設定頁。

### 4.2 不包含

v1 資料遷移、Markdown 匯出、自動鏡像（第 2 階段）；帳號、加密、同步（第 3 階段）；分享（第 4 階段）；知識圖譜、PWA、Mermaid、數學公式、區塊嵌入（第 5 階段）；註腳；多人協作；多個知識庫的切換介面（資料模型支援，介面第 1 階段只有一個知識庫）。

## 5. 技術選型

| 項目 | 選擇 | 理由 |
|---|---|---|
| 框架 | Vite + React + TypeScript | 純前端、無伺服器端渲染需求；Tauri 官方搭配；PWA 工具成熟 |
| 編輯器 | Tiptap 3 | 掌控度高、MIT 授權、ProseMirror 的中文輸入處理經實測可靠 |
| CRDT | Yjs（`y-prosemirror` 綁定 Tiptap） | 生態最成熟，同步、加密皆可外加 |
| 本機儲存 | IndexedDB，以 Dexie 管理 | 全瀏覽器穩定；內建版本升級 |
| 介面狀態 | Zustand | 輕量、按需重新繪製 |
| 樣式 | Tailwind v4 + 設計 token | token 限制隨意數值；複雜效果寫在元件旁的 CSS |
| 底層元件 | Radix UI | 只提供行為與無障礙，外觀自行設計 |
| 測試 | Vitest、Playwright | 單元、元件、端對端 |
| 部署 | Vercel（靜態） | 沿用現有專案，分支自動預覽 |

## 6. 架構分層

```
src/
  ui/          介面層：版面、共用元件、設計 token
  features/    功能層：editor, sidebar, rail, panel, search, settings, trash
  core/        核心層（純 TypeScript，不依賴 React）：vault, note-doc, indexer, search, preferences, ids, order
  adapters/    轉接層：storage（第 1 階段實作 IndexedDB）；sync / crypto / mirror / fs 介面預留
  workers/     背景執行緒：search
```

規則：
- 上層可以依賴下層，下層不得依賴上層
- 核心層不依賴 React，可單獨測試，日後桌面版與分享頁可重用
- 轉接層皆以介面定義，實作可替換
- 元件只透過核心層的指令改資料、只透過 hook 讀資料，不直接存取資料庫
- 單一檔案超過約 300 行即應拆分

## 7. 資料結構

### 7.1 識別碼
筆記、資料夾、區塊、附件、知識庫的 id 皆在裝置上產生（隨機、不重複，例如 21 字元的 nanoid），不需伺服器配發。

### 7.2 三種 Yjs 文件

**知識庫結構文件**（每個知識庫一份，guid = 知識庫 id）

```
meta:        Y.Map { schemaVersion, name, createdAt }
notes:       Y.Map<noteId, Y.Map {
               title, folderId | null, order,
               createdAt, updatedAt, deletedAt | null }>
folders:     Y.Map<folderId, Y.Map { name, parentId | null, order, createdAt, deletedAt | null }>
attachments: Y.Map<attachmentId, Y.Map { filename, mimeType, size, createdAt }>
```

- `order` 使用分數索引字串（fractional indexing），拖曳排序只改單一項目，多裝置同時排序不衝突
- `deletedAt` 非空即在垃圾桶；超過 30 天由 App 啟動時清除（刪除筆記文件與未被引用的附件）
- 刪除資料夾時，資料夾本身與其下所有子資料夾、筆記一起移入垃圾桶；還原時恢復原本的階層，原父資料夾已不存在則還原到最上層

**筆記文件**（每篇一份，guid = 筆記 id）

```
meta:    Y.Map { schemaVersion }
content: Y.XmlFragment   — Tiptap 文件內容
```

**個人偏好文件**（每位使用者一份）

```
prefs: Y.Map { accent, background, backgroundBlur, backgroundDim,
               fontSize, lineHeight, editorWidth, railMode,
               sidebarWidth, panelWidth, reduceMotion, reduceTransparency }
```

### 7.3 標題
- 標題只存於結構文件 `notes[id].title`。編輯器上方的標題區塊綁定此欄位，與檔案樹改名是同一份資料
- 新增與改名時檢查不重名（去除前後空白、不分大小寫）；重名時就地提示，不允許送出
- 同步造成的重名（第 3 階段）：較晚建立者自動加上「 (2)」並通知

### 7.4 連結與標籤（Tiptap 節點）
- `noteLink`（行內節點）：`{ noteId, blockId | null }`；顯示文字即時從結構文件取標題，區塊連結再附上目標區塊的前幾個字。無法指向不存在的筆記
- 目標筆記在垃圾桶或已刪除：顯示「已刪除的筆記」；目標區塊不存在：顯示「已刪除的區塊」
- `tag`（行內節點）：`{ name }`
- 每個區塊節點帶 `id` 屬性；新建與貼上時產生新 id，同一文件內不得重複

### 7.5 清單編號
- 編號清單依巢狀深度自動決定樣式：第 1 層數字、第 2 層字母、第 3 層羅馬數字，之後循環
- 單一清單可設定 `listStyle: decimal | alpha | roman` 覆蓋自動樣式

### 7.6 本機資料庫（Dexie，名稱 `notes-v2`）

| 資料表 | 欄位 | 性質 |
|---|---|---|
| `updates` | `docId`, `seq`, `data` | Yjs 增量（正本） |
| `snapshots` | `docId`, `data`, `upToSeq` | 壓縮後的文件快照（正本） |
| `blobs` | `attachmentId`, `blob` | 附件本體（正本） |
| `noteText` | `noteId`, `title`, `text`, `updatedAt` | 搜尋用純文字（衍生） |
| `links` | `sourceNoteId`, `sourceBlockId`, `targetNoteId`, `targetBlockId`, `snippet` | 反向連結（衍生） |
| `tags` | `noteId`, `tag` | 標籤統計（衍生） |
| `meta` | `key`, `value` | 上次開啟的筆記、索引版本等 |

- **不使用 `y-indexeddb`**：它為每份文件建立一個獨立的 IndexedDB 資料庫，筆記數千篇時會產生數千個資料庫。改由儲存轉接層把所有文件的增量寫入同一個 `updates` 表
- 同一文件的增量超過 200 筆時合併為快照並刪除舊增量
- 衍生資料表可隨時整個重建

## 9. 主要流程

**打開 App**：開啟儲存層 → 申請持久儲存（`navigator.storage.persist()`）→ 載入結構文件與偏好文件 → 畫出資料夾樹 → 開啟 `meta.lastNoteId` 那一篇（只載入這一篇）。首次開啟時建立預設知識庫與一篇歡迎筆記。

**編輯筆記**：編輯器修改 → Yjs 文件更新 → 增量立即寫入 `updates` → 廣播給其他分頁 → 停止輸入約 1 秒後 indexer 更新衍生資料 → 反向連結、搜尋即時反映。

**改名**：標題區塊或檔案樹修改 → `vault.renameNote()` 檢查不重名 → 寫入結構文件 → 所有顯示該標題的連結自動更新（不需改動任何筆記文件）。

**移動筆記**：側欄拖曳 → `vault.moveNote()` → 只改結構文件的 `folderId` 與 `order`。

**建立區塊連結**：輸入 `[[` → 選筆記 → 輸入 `#` 搜尋該筆記的標題與段落（來源：`noteText` 與筆記文件）→ 插入 `noteLink { noteId, blockId }`。或從區塊把手選「複製區塊連結」後貼上。點擊連結 → 開啟目標筆記 → 捲動至區塊並短暫反白。

**搜尋**：輸入 → 背景執行緒在 `noteText` 逐篇比對 → 排序：標題命中 > 標籤命中 > 內文命中，同級依修改時間新到舊 → 顯示命中片段。

**反向連結**：已連結 = 查 `links` 中 `targetNoteId` 為目前筆記者；提到但未連結 = 在 `noteText` 中搜尋目前標題、排除已連結者。「轉為連結」把該處文字換成 `noteLink`。

## 10. 編輯器細節

- 標題區塊在 Tiptap 內容之上，視覺上為內文第一行；按 Enter 移入內文，在內文第一行按上方向鍵回到標題
- Slash 選單：輸入 `/` 開啟，可輸入篩選，方向鍵與 Enter 選擇，Esc 關閉；組字中不觸發
- 浮動格式列：選取文字時出現於選取範圍上方；液態玻璃材質
- 拖曳把手：滑到區塊左側出現，可拖曳排序，點擊開啟選單（轉換類型、複製區塊連結、刪除）
- 程式碼區塊：語言選擇；ABAP 使用自訂高亮規則
- 表格：插入預設 3×3；增刪列與欄、拖曳調整欄寬；Tab 在儲存格間移動
- 中文輸入法：所有自訂鍵盤行為在組字期間（`isComposing` 或 keyCode 229）不攔截
- 貼上：純文字依段落切分；Markdown 文字轉為對應區塊；HTML 只保留支援的格式

## 11. 介面設計

### 11.1 版面（D 方案）
- 使用者背景鋪滿視窗；左側卡片（資料夾樹）與中間筆記卡片浮在背景上
- 隱藏式圖示工具列（檔案、搜尋、標籤、設定）：滑鼠移至視窗左緣時從左側滑出，垂直置中，浮於側欄之上不推動版面；快捷鍵 `Ctrl + \`（macOS `⌘ + \`）切換；設定可改為固定顯示
- 右側卡片：點筆記上方膠囊的「大綱」或「反向連結」從右側滑出，可切換分頁，× 或 Esc 收回

### 11.2 自動調整版面

| 視窗寬度 | 左側卡片 | 右側卡片 |
|---|---|---|
| ≥ 1440px | 並排常駐 | 打開時並排 |
| 1100～1439px | 並排常駐 | 打開時浮在筆記上方 |
| < 1100px | 自動收起，點工具列「檔案」浮出 | 打開時浮在筆記上方 |

側欄寬度 220～360px、右側卡片寬度 280～420px，可拖曳調整並記住。

### 11.3 設計原則
一致的間距節奏（4px 為基數）、層次靠字重與留白而非框線、單一強調色、彈簧曲線動畫、版面不跳動、每個狀態都有設計、毛玻璃與細微陰影表現深度、單一風格的線條圖示。

### 11.4 字型
字型順序：Apple 系統字（SF、蘋方）→ 思源黑體（Noto Sans TC）→ 一般無襯線字。思源黑體以 `@fontsource` 自行託管並依 unicode-range 分片，僅下載用到的字，不向外部字型服務發出請求。

### 11.5 強調色
介面中唯一的彩色，用於目前選中的項目、連結、主要按鈕、勾選、提示圖示、反白。預設靛紫 `#4F4BC9`；設定頁提供 8 種精選色，每一種在淺色背景上的文字對比皆需 ≥ 4.5:1。

### 11.6 設定頁

| 類別 | 項目 |
|---|---|
| 背景 | 上傳圖片、模糊度、淡化程度、恢復預設 |
| 色彩 | 強調色 |
| 文字 | 字級（小／標準／大）、行距、編輯區寬度（窄／標準／寬） |
| 版面 | 工具列（滑鼠觸發／固定顯示）、側欄寬度 |
| 動態 | 減少動態效果、減少透明度：各為「跟隨系統／開啟／關閉」，預設跟隨系統 |

背景太雜時自動加強模糊與白色遮罩，確保側欄文字對比。

## 12. 錯誤處理

| 情況 | 處理 |
|---|---|
| 多分頁開啟 | `tabs-bridge` 互傳增量，內容即時一致 |
| 儲存空間不足 | 寫入失敗時頂部提示原因與建議（匯出、刪除大型附件）；未寫入的內容保留在記憶體並重試 |
| 無痕模式或禁止儲存 | 啟動時偵測並告知關閉後資料會消失，仍可使用 |
| 持久儲存被拒 | 設定頁顯示狀態與說明 |
| 單篇筆記損壞 | 只有該篇顯示錯誤；保留原始資料不覆蓋 |
| 索引不一致 | 背景自動重建；設定頁提供「重建索引」 |
| 寫入中途關閉 | 增量為原子寫入，最多遺失最後一次未寫入的修改 |
| 格式版本升級 | 文件與資料庫各有版本號，啟動時先備份再升級 |
| 附件過大 | 單一附件上限 100 MB，超過時提示 |

錯誤訊息一律說明「發生了什麼、可以怎麼做」，不顯示技術代碼；技術細節寫入背景記錄。

## 13. 測試與品質

- **核心層單元測試（Vitest）**：vault 各指令、不重名規則、排序、垃圾桶、indexer、搜尋排序、儲存轉接層的寫入與壓縮。核心層採測試先行
- **編輯器測試（Vitest + jsdom）**：各自訂區塊、清單縮排與編號、Slash 選單、標題區塊、連結節點
- **端對端測試（Playwright，Chromium 與 WebKit）**：新增筆記 → 打字 → 加連結與區塊連結 → 重新整理後內容仍在 → 反向連結出現；改名後連結更新；搜尋中文片段；多分頁同步
- **手動清單**：中文輸入法（沿用輸入法測試台的 12 個情境，含已知問題「待辦清單中輸入數字順序顛倒」），每個大版本在 Windows Chrome 與 macOS Chrome 執行
- **GitHub Actions**：每次推送執行型別檢查、Lint、全部自動測試、建置；任一失敗不合併
- **效能門檻**：1,000 篇筆記的知識庫，冷啟動到可編輯 < 1.5 秒；搜尋回應 < 100 毫秒；一般輸入每次按鍵處理 < 16 毫秒

## 14. 開發與部署流程

- v1 保存在 `v1-archive` 分支；`main` 在切換前維持 v1 不變，正式網站照常運作
- v2 在 `v2` 分支開發；Vercel 為 `v2` 提供預覽網址
- 切換條件：第 1 階段完成且第 2 階段的 v1 資料自動遷移完成。切換前請使用者從 v1 匯出 ZIP 備份，再將 `v2` 合併進 `main`，接手原網址；新版首次開啟時讀取同網址下 v1 的 `WebObsidianDB` 自動轉換
- 合併至 `main`、刪除分支或資料、會產生費用的動作，須事先取得使用者同意

## 15. 已知問題與風險

- **待辦清單內輸入數字順序顛倒**（Windows Chrome + 注音，輸入法測試台發現）：重寫待辦區塊時須修正，列入手動清單
- **毛玻璃效能**：在一般 Windows 筆電可能吃效能；以「減少透明度」設定與偵測系統設定作為退路
- **瀏覽器自動清除資料**：以持久儲存降低風險；第 2 階段的鏡像與第 3 階段的同步為根本解法
- **Supabase 免費方案限制**（第 3 階段）：一週無活動會暫停專案、儲存容量有限；同步層可替換
